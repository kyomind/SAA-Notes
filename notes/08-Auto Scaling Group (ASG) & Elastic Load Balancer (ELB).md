# 08-Auto Scaling Group (ASG) & Elastic Load Balancer (ELB)

2025-10-08

---

## 🌩️ Auto Scaling Group (ASG) 核心概念

### ✅ 定義

**Auto Scaling Group** 是一個自動化機制，用來根據系統負載自動調整 **EC2 實例數量**。

* 可根據流量自動增加或減少伺服器數量
* 確保系統在高峰時維持效能、低谷時節省成本
* 可與 **CloudWatch** 整合以根據監控指標觸發縮放

### 🧠 類比

像是一個會根據流量自動幫你「加派或減少伺服器」的智慧管理員。

### 💡 考試重點

> **ASG 的核心用途：** 自動調整 EC2 實例數量以符合需求。

### 📘 補充重點

| 元件                | 功能                                                       | 範例                       |
| ------------------- | ---------------------------------------------------------- | -------------------------- |
| **Launch Template** | 定義 EC2 啟動設定（AMI、Instance Type、Security Group 等） | ASG 啟動新實例時會用到     |
| **Scaling Policy**  | 決定何時擴展/縮減                                          | 例如：CPU > 70% 時自動擴展 |
| **Cooldown Period** | 縮放後的冷卻時間，避免頻繁重複調整                         | 預設 300 秒                |

### 🧩 Scaling Policy 類型

| 類型                  | 特點                                     | 使用時機                   |
| --------------------- | ---------------------------------------- | -------------------------- |
| **Target Tracking**   | 自動追蹤指標（如 CPU 使用率維持在 50%）  | 最常用、建議使用           |
| **Simple Scaling**    | 單一條件觸發（例如 CPU > 80% 就加一台）  | 簡單場景                   |
| **Step Scaling**      | 根據負載程度分級調整（加 1 台、加 2 台） | 複雜負載變化               |
| **Scheduled Scaling** | 預設時間點調整容量                       | 已知流量高峰（如促銷活動） |

> 🧭 **考試提醒**：遇到題目提到「自動根據負載維持穩定性能」→ 選 **Target Tracking Scaling Policy**。

## ⚖️ Elastic Load Balancer (ELB) 核心概念

### ✅ 定義

**ELB** 負責將流量平均分配到多台後端 EC2 實例，確保應用程式的 **高可用性** 與 **彈性**。

### 🧠 類比

就像是一個智慧分流器，負責把使用者請求平均分配給後端伺服器。

### 📘 類型比較

| 類型                                | 適用層級    | 使用場景                               |
| ----------------------------------- | ----------- | -------------------------------------- |
| **ALB (Application Load Balancer)** | Layer 7     | HTTP/HTTPS、微服務、基於路徑或主機分流 |
| **NLB (Network Load Balancer)**     | Layer 4     | 超高效能、TCP/UDP 服務（如遊戲伺服器） |
| **CLB (Classic Load Balancer)**     | Layer 4 & 7 | 舊版系統，考試幾乎不再出現             |

### 💡 DNS 而非 IP

* ELB 提供的是 **DNS 名稱**（例如：`myapp-123456.elb.amazonaws.com`）
* 背後實際有多個 IP 供彈性擴展與高可用性使用
* 這樣做可避免單點故障並允許動態調整實例

> ⚠️ **考試陷阱提醒**：ELB **沒有固定 IP**，題目若問「如何讓使用者不受背後實例變動影響」→ 答案是「透過 ELB 的 DNS 名稱」。

## 🔄 ASG + ELB 整合架構

### 🧩 架構關係

* **ELB**：負責分流請求給健康的實例。
* **ASG**：根據負載自動增加或減少這些實例。

兩者搭配後：

1. ELB 接收使用者請求並分配到 ASG 內的健康實例。
2. ASG 自動根據 CloudWatch 指標擴展或縮減實例。
3. ELB 會自動偵測新實例並加入流量分配池。

### 🧱 考試常見題型

> 題目提到「流量高峰時要自動擴展、低峰時自動縮減，且確保使用者請求平均分配」→ 選 **ELB + ASG 組合**。

---

## 📡 監控與觸發機制

### 監控來源

* **Amazon CloudWatch**：監控 EC2、ASG、ELB 的運作狀況與指標。

### 常見監控指標

| 指標               | 意義           | 可能動作       |
| ------------------ | -------------- | -------------- |
| CPUUtilization     | CPU 使用率過高 | 擴展實例       |
| NetworkIn / Out    | 網路流量上升   | 擴展實例       |
| RequestCount       | 請求數量上升   | 擴展實例       |
| UnhealthyHostCount | 不健康實例增加 | 停止或替換實例 |

> 🧩 **考試重點：** CloudWatch 是 ASG 的「觸發條件來源」，沒有它就無法自動判斷何時調整。

## 🧠 總結思維導圖

```
使用者請求
     ↓
  [ ELB - 分流器 ]
     ↓
  [ ASG - 動態實例群組 ]
     ↓
  [ EC2 實例 - 根據 Launch Template 啟動 ]
     ↑
  [ CloudWatch - 監控並觸發 Scaling Policy ]
```

---

## 🏁 考試速記重點

> **ASG：** 自動調整 EC2 數量。
>
> **ELB：** 分配流量，提供 DNS 而非固定 IP。
>
> **ASG + ELB：** 彈性擴展 + 高可用架構。
>
> **CloudWatch：** 提供監控指標與觸發縮放條件。
>
> **Launch Template：** 定義 EC2 的啟動配置。
>
> **Scaling Cooldown：** 防止頻繁擴縮，讓系統穩定下來。
